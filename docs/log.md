## 2026-11-06

* **Visible name**: the owner chose **Day Planner** (#1). `.desktop` `Name`, metainfo `<name>`, window title, sidebar header and About dialog say Day Planner, the nightly "Day Planner (Nightly)"; repository, app id, package and docs keep the code name Pensum ([app name](decisions/app-name.md)).
* **Repeating tasks** (#12): `pensum/store/repeat/` creates instances the way Super Productivity does (schedule, instances, rules) at start, after an import and on day change (`pensum/day_watch.py`); the task page has a Repeat page with presets, custom schedules, pause and Stop Repeating with Undo. Defaults for a new rule come from `DEFAULT_TASK_REPEAT_CFG` in `sp-defaults.json` ([data](super-productivity-data.md), [features](features.md)). Found on the way: replacing a combo row's list from inside its own `notify::selected` blocks GTK, so the page redraws on idle.
* **QuestArc's journeys** (#38, #39, #40): `pensum/game/` runs QuestArc's engine through gjs (`evaluateHost`, `diff`, `action`), keeps QuestArc's choice records in `pluginUserData` (`questarc:<key>`, `GZ1:` from 1024 characters), reads the journeys and texts from QuestArc's release archive and sets up a stage's task with its repeat rule in one go. `pensum/ui/journey/` shows the journey page (banners, card, path, main action in the bottom bar) and the choose, start, set-up, continue, station, weekly look back, shelf and motivation pages; Preferences → Journeys has calm or game and removing the data. The demo dataset walks "First Things First". Found on the way: a background evaluation that finished late overwrote a newer view, so results carry a generation; drawing with Cairo needs `python3-gi-cairo` on the host ([journeys](journeys.md), [development environment](dev-environment.md)).
* **QuestArc 3.1.0 pinned**: the manifest installs QuestArc's engine archive v3.1.0 (`questarc-engine`, sha256 checked against the release's `SHA256SUMS`) to `/app/share/questarc`, with both licence texts; CI now fetches it and requires the engine tests. All 113 tests pass against the archive ([dependencies](dependencies.md), [journeys](journeys.md)).
* **Back swipe from a list to the lists**: reported missing by the owner. With real touch events in a headless Mutter the swipe works on `main` (also when the window starts wide and is maximised later) and does nothing in v0.1.0, the current stable release, which predates the single navigation view ([design](design.md)). The stable release needs the next version.
* **Swipe back to the lists, Ephyra's way**: the owner reported that the swipe from a list back to the lists is missing, unlike Ephyra and Nauta. The window now uses Ephyra's layout: the navigation view's first page holds an `AdwNavigationSplitView` (lists as sidebar, the list or Journeys as content, collapsed below 600 sp); other pages are pushed on top. The hand-made move of the lists between a page and an `AdwOverlaySplitView` is gone. Checked with real touch events in a headless Mutter; tests check the layout ([design](design.md)).
* **Journey opening after every change**: reported by the owner. The set-up page's model listener outlived the page (a popped `AdwNavigationPage` is never destroyed while the model holds its callback), so after a stage's task was created every change in the lists showed the journey. Pushed journey pages now subscribe with `JourneySubpage.listen()`, which ends with the page's place on the navigation stack; as the owner asked, the journey comes forward only for a new completion of the current station's own task ([journeys](journeys.md)). A UI test fails on the old code and passes now; 114 tests with the engine.
* **Changing a task's project crashed the app**: reported by the owner. Choosing a project on the task page redrew the page, which replaced the project row's list while the row was still handling the selection; GTK segfaults then (the same trap as the repeat page's combo rows). The move now runs on idle, and the list is only replaced when the projects' names changed. A UI test fails on the old code; 110 tests pass without the engine (the engine's gjs comes from Flathub, which the cloud container could not reach this time).
